# ADR-004: M0-04 CI와 필수 검사 구성

- 상태: 사용자 승인 (2026-10-27, Asia/Seoul). 로컬 구현 승인과 원격 쓰기 승인은 별개다.
- 범위: [TASKS M0-04](../TASKS.md#m0-04-ci), TASKS 버전 0.2. M0-05 배포와 M0 릴리스는 포함하지 않는다.
- 저장소: 공개 `songstone/four-lane-auction`.
- 선행: M0-03 완료. 시작 SHA `ede60ae2a6f6b28d3c00162a96dd9f4c3c125abf`, 최신 `dev`에서 `feature/M0-04-ci` 생성.

## 비교한 대안과 결정

| 항목 | 결정 | 대안과 선택 이유 |
|---|---|---|
| 트리거 | `dev`·`main` push와 두 브랜치 대상 `pull_request` | feature push 추가는 PR 실행과 중복되므로 제외. PR head 갱신은 `synchronize` 이벤트로 검사한다 |
| 경로 필터 | 경로에 관계없이 두 잡 항상 실행 | 워크플로 `paths` 필터는 문서 전용 변경 등에서 필수 검사가 Pending으로 남을 수 있다. 잡 단위 변경 감지는 감지 실패·스킵·실패 전파를 처리하는 고정 게이트가 더 필요해 이번 범위에서는 선택하지 않았다 |
| 검사 이름 | `backend`, `frontend` | 의존 관계와 조건부 잡 생략 없이 각자 실행하고 실패한다. `.github/workflows/**` 변경 때도 둘 다 실행한다 |
| 백엔드 진입점 | `./gradlew --no-daemon clean build --no-build-cache` | 기존 M0-02 진입점을 사용한다. `verifyTimeSources`, engine/app 빌드, UTC `test`, 서울 `testSeoul`이 포함된다. `clean`과 빌드 캐시 비활성화로 이전 테스트 결과를 실제 실행으로 세지 않는다 |
| 실행 환경 | GitHub-hosted `ubuntu-24.04`, Corretto 21, Node 24 | 백엔드 Java 21 toolchain과 프론트 engines에 맞춘다. Testcontainers는 러너의 Docker를 사용하며 Compose MySQL을 별도로 띄우지 않는다 |
| 린트 | ESLint flat config, JS·TS recommended, Hooks 호출·의존성 규칙 | Biome 대신 승인한 ESLint 규칙 조합을 사용한다. 생성 코드·빌드 산출물은 제외하고 경고도 실패 처리한다 |
| TypeScript 호환성 | **7.0.2 → 6.0.3** (사용자 추가 승인) | 최신 안정 `typescript-eslint 8.72.1`의 peer 범위가 `>=4.8.4 <6.1.0`이다. 호환 최신 안정 6.0.x로 조정하도록 사용자가 선택했다. 강제 설치·peer 검사 무시·지원 경고 숨김은 사용하지 않는다 |
| 캐시 | Gradle `setup-gradle`, npm `setup-node` | 의존성 다운로드를 재사용한다. Gradle 캐시 쓰기는 main/dev push만, PR은 읽기만 허용한다. setup-java의 Gradle 캐시와 중복 사용하지 않고 node_modules도 캐시하지 않는다 |
| 테스트 실행 증거 | JUnit XML을 검증하고 Actions 요약 및 artifact에 보존 | 빌드 성공 표시만으로 Testcontainers 실행을 판단하지 않는다. 아래 검증 조건을 모두 만족해야 한다 |
| 보호 규칙 | main/dev PR 필수, 두 검사 필수, 최신 기준 브랜치 요구, 관리자 우회 금지, 승인 리뷰 0개 | `strict=false` 대신 최신 통합 결과를 요구한다. 마지막 push 승인·코드 소유자 승인을 추가하지 않는다. force push·브랜치 삭제·우회 허용 목록도 허용하지 않는다 |
| 머지 방식 | merge commit만 허용 | squash와 rebase는 비활성화한다. AGENTS의 `--no-ff` 원칙과 맞춘다. 머지는 사용자만 한다 |
| GitHub 도구 | gh 2.103.3 설치 (사용자 승인) | 인증은 사용자 계정으로 한다. 토큰을 채팅·저장소·로그에 남기지 않는다 |

보호·머지 설정은 위와 같이 결정했지만 **이 문서가 원격 적용의 증거는 아니다**. 첫 PR의 실제 검사 이름·발행 앱을 확인하고, 명령과 JSON을 보여준 뒤 별도 승인을 받아 적용한다.

## 테스트 리포트 검증

`.github/scripts/verify-test-results.py`는 Python 표준 라이브러리만 사용한다.

- `test`(UTC), `testSeoul`(Asia/Seoul)마다 app의 `SchemaAndTimeIntegrationTest`와 `SessionHttpAndStompIntegrationTest` 리포트가 있어야 한다. 두 클래스는 기존 `MySqlIntegrationTest`를 상속하고 실제 MySQL Testcontainers를 사용한다.
- 각 필수 클래스의 실행 수(`tests - skipped`)는 0보다 커야 한다. 모든 보고된 테스트의 failures/errors/skipped는 0이어야 한다.
- XML의 집계 속성과 실제 testcase·failure·error·skipped 요소 수도 대조한다. 누락·손상·집계 불일치는 실패다.
- 태스크·시간대·클래스별 수와 전체 수를 stdout·`GITHUB_STEP_SUMMARY`에 기록한다. UTC와 서울은 같은 테스트를 다른 JVM에서 실행한 횟수로 구별한다.
- Gradle 실패 후에도 취소되지 않았고 빌드를 시도했다면 리포트를 진단한다. 원래 실패는 숨기지 않는다. 리포트가 있으면 실패 시에도 XML·HTML artifact를 14일 보존한다.
- Docker 부재·이미지 다운로드·DB 시작 실패를 skip 처리하지 않는다. `docker info`와 기존 `@Testcontainers` 구성으로 실패한다.

## 적용·검증 순서

1. main/dev를 먼저 원격에 올린다. 이번에는 시작 시 두 브랜치가 같은 시작 SHA로 원격에 존재함을 확인했다. 재게시·원격 추가는 필요하지 않았다.
2. 최신 dev에서 feature를 만들고 로컬 검증을 완료한다. push와 dev 대상 PR 생성의 실제 명령·JSON을 제시하고 별도 승인을 받는다.
3. feature PR에서 첫 CI를 실행한다. 성공한 check-run에서 실제 검사 이름과 발행 GitHub App을 확인한다.
4. 두 브랜치 보호와 머지 방식의 실제 명령·JSON을 제시하고 별도 승인 후 설정한다. 설정 조회 결과와 첫 성공을 보고한다.
5. 사용자가 구현 PR을 merge commit으로 머지한다. 에이전트는 머지하지 않는다.
6. 최신 dev에서 `feature/M0-04-ci-failure`를 만들고 운영 Java에 `Instant.now()` 위반을 추가한다. push·dev 대상 PR 생성의 별도 승인 후 backend 실패·frontend 독립 실행·필수 검사에 의한 머지 차단을 확인한다.
7. 별도 승인받은 비강제 push로 관리자를 포함한 main/dev 직접 push 거절과 전후 원격 SHA 불변을 측정한다. 실패 PR은 머지하지 않고 닫는다.
8. 성공/실패 Actions 링크 2개, 테스트 실행 수, 머지 차단 화면, 보호 설정 조회 결과, 직접 push 거절 로그, 실패 PR의 미머지 종료를 최종 보고한다. 구현 PR 머지 후 증거는 기존 PR 본문과 최종 보고에 추가하고 dev에 직접 커밋하지 않는다.
