# Four-Lane Auction — 아이디어 & 결정 사항

> 웹 기반 멀티레인 실시간 경매 플랫폼. 회차(Session)마다 1~4개 레인이 동시에 진행되고, 각 레인에서는 출품물(Lot)이 순서대로 하나씩 경매된다. 입찰자는 한 화면에서 모든 레인을 실시간으로 보며 원하는 레인에 입찰한다.

- 형태: 1인 취업용 포트폴리오 (Spring Boot 백엔드 중심)
- 개발 방식: **AI 에이전트를 활용한 병렬 개발.** 백엔드와 프론트엔드를 동시에 진행한다
- 기간: 10주
- 프론트엔드: React. 범위는 줄이지 않고 계획대로 간다
- 배포: 단일 인스턴스로 시작 (scale-out은 스트레치 목표)

이 문서는 PM/아키텍트 인터뷰(6라운드) 결과다. `(가정)`이 붙은 항목은 인터뷰에서 명시적으로 정하지 않아 기본값으로 둔 것이며 바뀔 수 있다.

## 1. 경매 대상 도메인

- **C2C 중고 물품 경매.** 당근마켓처럼 일반 회원이 자유롭게 물품을 출품한다.
- 레인 수는 하드코딩하지 않는다. 회차마다 **1~4개 레인**을 가변으로 운영한다.
- 출품물에는 이미지가 필수다. (가정) 로컬 스토리지 어댑터로 시작하고, 나중에 S3로 교체할 수 있게 인터페이스로 분리한다.

### 핵심 도메인 모델

```
Member ─┬─< Item (출품물, 판매자 소유)
        │      └─< Lot (특정 회차·레인·순번에 편성된 경매 1건. 재출품하면 Lot이 새로 생성됨)
        │
Session (회차) ─< Lane (1~4) ─< Lot (순번 순서대로)
                                  └─< Bid
Lot(낙찰) ── Trade (거래) ── Payment (모의 결제)
```

- **Item과 Lot을 분리한다.** 유찰된 물품을 재출품하면 같은 Item에 새 Lot이 생긴다. 출품 이력을 그대로 보존할 수 있다.

## 2. 경매 방식

| 항목 | 결정 |
|---|---|
| 방식 | 영국식(가격이 올라가는 방식) |
| 입찰 UI | **"다음 호가로 입찰" 버튼만 제공.** 금액 직접 입력 없음 |
| 호가 단위 | 현재가 1만 원 미만이면 +1,000원, 10만 원 미만이면 +10,000원, 그 이상이면 +25,000원 |
| 호가 정책 변경 | 운영자가 변경 가능. DB에 버전으로 관리하고, **회차 시작 시 그 시점의 정책을 스냅샷으로 고정**. 변경 사항은 다음 회차부터 적용 |
| 시작가 | 판매자가 지정. **첫 입찰 금액 = 시작가** (가정) |
| 최저 낙찰가 | 판매자가 비공개로 지정. 반드시 시작가 이상. 최고가가 최저 낙찰가에 못 미치면 유찰. 화면에는 "최저가 미달" 배지만 노출 |
| 자동 입찰(프록시 입찰) | **제외** |

### 입찰 검증 순서

1. 인증된 회원일 것
2. 입찰 정지 상태가 아닐 것 (미결제 패널티)
3. 본인이 출품한 물품이 아닐 것
4. 레인이 진행 중이고, 해당 Lot이 입찰을 받는 단계일 것
5. 클라이언트가 보낸 "내가 본 현재가"(`expectedPrice`)가 서버의 현재가와 같을 것. 다르면 `409 Conflict`
6. 입찰 금액이 "현재가 + 호가 단위"(첫 입찰이면 시작가)와 같을 것
7. 멱등 키가 중복이 아닐 것 (중복 클릭 방지)
8. (가정, 추가 제안) **현재 최고 입찰자는 연속으로 재입찰할 수 없다.** 의미 없는 가격 올리기를 막기 위함

### 백엔드 과제
- 호가 정책은 Strategy 객체로 분리하고, 구간 경계값(9,999 / 10,000 / 99,999 / 100,000원)을 테스트한다.
- 동일 호가 동시 입찰은 `expectedPrice` 비교로 **먼저 도착한 1건만 성공**시킨다.
- 최저 낙찰가가 외부로 새지 않도록 내부 도메인 객체와 외부 공개용 DTO를 분리한다.

## 3. 레인 진행 규칙

### 3.1 출품 → 편성 흐름

```
판매자 등록 → 검수 대기 → (운영자) 승인 / 반려
                           └ 승인 → 운영자가 회차·레인·순번 편성 → 회차 시작 시 편성 잠금
```

- 편성은 운영자가 직접 한다.
- **회차가 시작되면 편성을 바꿀 수 없다.**

### 3.2 Lot 진행: 카운트다운 리셋형

| 파라미터 | 값 |
|---|---|
| 첫 입찰 대기 시간 | Lot 시작 후 15초 동안 입찰이 없으면 유찰 |
| 입찰 시 리셋 | 입찰이 들어올 때마다 카운트다운 10초로 리셋. 10초 동안 입찰이 없으면 마감 |
| Lot 최대 길이 | **없음.** 입찰이 계속 들어오면 무제한으로 진행 |
| Lot 간 간격 | 5초 (결과 표시 + 다음 Lot 미리보기) |

- 위 값들은 회차 설정으로 빼서 조정할 수 있게 한다.
- **레인끼리 동기화하지 않는다.** 레인마다 독립적으로 다음 Lot으로 넘어간다.
- 회차 종료는 "모든 레인이 끝남"을 집계해서 판정한다.
- Lot 최대 길이가 없으므로 **회차 종료 시각은 예측할 수 없다.** UI에는 "현재 N번째 / 남은 Lot 수"만 표시한다.

### 3.3 Lot 상태와 마감 판정

```
SCHEDULED → WAITING_FIRST_BID(15초) → BIDDING(10초 카운트다운, 입찰마다 리셋)
         → (마감) SOLD : 최고가 ≥ 최저 낙찰가
                  UNSOLD : 입찰 없음 / 최저가 미달 / 운영자 강제 종료
```

- **마감 판정은 서버가 찍은 시각으로만 한다.**
- 입찰, 타이머 만료, 운영자 명령을 **모두 레인 단위 직렬 큐(단일 스레드 이벤트 루프)로 처리**한다. 그래야 "마지막 순간의 입찰"과 "타이머 만료"가 경합하지 않는다.
- 테스트에서 시간을 마음대로 조작할 수 있도록 `Clock`을 주입받는다.

### 3.4 유찰

- 그대로 종료한다. 판매자가 "재출품"을 누르면 다시 검수 대기로 돌아간다.
- **조건부 낙찰(최저가 미달 시 판매자와 최고 입찰자의 협상)은 제외.**

### 3.5 운영자 개입

| 기능 | 결정 |
|---|---|
| 일시정지·재개 | 레인 단위와 회차 전체 일괄, 둘 다 제공 |
| 재개 시 남은 시간 | 정지 시점의 남은 시간을 복원. 단 10초 미만이면 10초로 보장 |
| Lot 강제 종료 | 포함 (유찰로 처리) |
| 특정 입찰 취소(롤백) | **제외** |
| 감사 로그 | 모든 운영자 조치를 기록 |

- 일시정지 명령도 입찰과 같은 레인 직렬 큐로 들어간다. 따라서 정지 직후에 도착한 입찰은 일관되게 거절된다.

### 3.6 장애 복구

- 입찰은 **DB에 커밋한 뒤에 성공 응답**한다. 메모리는 캐시이고, 원본 데이터는 DB다.
- 서버가 재시작되면 진행 중이던 레인을 **일시정지 상태로 복구**한다. 현재 최고가와 최고 입찰자는 DB에서 읽어온다. 운영자가 재개하면 카운트다운 10초부터 다시 시작한다.
- 이벤트 소싱으로 완전 복원하는 방식은 범위 밖이다.

## 4. 사용자 역할과 권한

| 역할 | 권한 |
|---|---|
| 비로그인 관전자 | 회차와 레인 실시간 관전 (WebSocket 구독) |
| 일반 회원 (`USER`) | 관전 + 출품(판매자) + 입찰(입찰자). 판매자와 입찰자를 겸함 |
| 운영자 (`ADMIN`) | 검수·승인, 회차 편성, 진행 제어(일시정지·재개·강제 종료), 호가 정책 관리 |

- **본인이 출품한 물품에는 입찰할 수 없다.** 역할이 아닌 도메인 규칙이므로 입찰 검증 로직 안에서 처리한다.
- 인증은 JWT(Access + Refresh)를 쓴다. (가정) 단일 인스턴스이므로 Refresh Token은 DB에 저장한다.
- WebSocket(STOMP)은 **구독은 익명으로 허용하고, 개인 큐는 인증된 사용자만** 쓸 수 있다. 연결 시점에 JWT를 검증하는 인터셉터를 둔다.

## 5. 낙찰 이후 흐름

```
Lot SOLD → Trade 생성 → AWAITING_PAYMENT ─┬ 모의 결제 성공 → COMPLETED
                                          └ 결제 기한 초과 → CANCELED + 낙찰자 경고 1회
```

| 항목 | 결정 |
|---|---|
| 구현 범위 | 낙찰 → 결제 대기 → 모의 결제 → 거래 완료 |
| 결제 | 내부 가짜 결제 모듈. 결제 연동 부분은 인터페이스로 분리해서 PG 테스트 모드로 교체할 수 있게 둠. 결제 요청은 멱등 처리 |
| 결제 기한 | 24시간. 시연을 위해 설정으로 짧게 바꿀 수 있음 |
| 미결제 패널티 | 거래 자동 취소 + 경고 누적. (가정) **경고 3회면 입찰 정지** |
| 차순위 입찰자 승계 | **제외** |
| 정산·배송 | **제외** |

### 알림

- 접속 중이면 WebSocket 개인 큐(`/user/queue/notifications`)로 즉시 보내고, 같은 내용을 DB 알림함에도 저장한다.
- 알림 종류: 상위 입찰에 밀림, 낙찰, 유찰(판매자), 결제 기한 임박, 거래 취소, 검수 결과
- 이메일은 제외한다.

## 6. 아키텍처 핵심 결정

| 항목 | 결정 |
|---|---|
| 입찰 통로 | **REST** `POST /api/lanes/{laneId}/bids` (`Idempotency-Key` 헤더, `expectedPrice` 포함) |
| 실시간 브로드캐스트 | WebSocket + STOMP. Spring 내장 메시지 브로커(Simple Broker)로 시작 |
| 브로드캐스트 메시지 | 레인별 단조 증가 시퀀스 번호와 서버 시각을 포함. 클라이언트가 번호 누락을 감지하면 REST로 레인 스냅샷을 다시 받아옴 |
| 레인 실행 방식 | 레인마다 단일 스레드 이벤트 루프(직렬 큐) + 타이머 |
| 레인 상태 저장소 | 인터페이스로 분리. 지금은 메모리 구현, 나중에 Redis 구현으로 교체 가능 |
| 응답 코드 | 409 이미 다른 입찰이 들어옴 / 403 입찰 정지 또는 본인 물품 / 422 Lot이 입찰을 받지 않는 상태 |

(가정) 기술 스택: Java 21, Spring Boot 3.x, Spring Data JPA, MySQL 8, Spring Security, React + TypeScript

## 7. 목표 규모와 증명 계획

### 7.1 목표 수치

| 지표 | 목표 |
|---|---|
| 동시 WebSocket 연결 | **5,000** (스트레치 목표 10,000). 단일 인스턴스 기준 |
| 입찰 시도 처리량 | 전체 초당 1,000건 (4레인 × 레인당 250건). 대부분은 409 거절 |
| 입찰 응답 시간 | p99 100ms 미만 |
| 브로드캐스트 전달 지연 | 입찰 확정부터 관전자 5,000명 수신까지 p99 300ms 미만 |
| 정합성 | 동일 호가 동시 입찰 N건 중 정확히 1건만 성공. 최종 낙찰자가 DB 입찰 이력과 100% 일치. 유실 0건, 중복 낙찰 0건 |

### 7.2 측정 환경

- 부하 테스트: **k6**. HTTP 입찰과 WebSocket 관전자 시나리오를 함께 작성하고, STOMP 프레임은 직접 구성한다.
- 모니터링: Micrometer + Prometheus + Grafana
- 커스텀 메트릭: 입찰 처리 시간, 레인 큐 적체량, 브로드캐스트 지연, 연결 수
- 환경: 서버와 부하 발생기를 **다른 머신**에 둔다 (예: AWS EC2 2대). 브로드캐스트 지연을 측정하려면 두 머신이 NTP로 시계를 맞춰야 한다.
- 정합성 검증: 부하 테스트가 끝난 뒤 DB 입찰 이력을 다시 돌려서 최종 낙찰자를 확인하는 스크립트

### 7.3 전후 비교 실험

1. **입찰 동시성 제어:** DB 비관적 락 vs 낙관적 락 vs 레인별 직렬 큐. 처리량, p99 응답 시간, 정합성을 비교한다. "왜 레인별 직렬 큐를 선택했나"를 수치로 정당화하는 것이 목적이다.
2. **브로드캐스트 최적화:** 수신자마다 메시지를 직렬화하는 방식 vs 1회 직렬화 후 공유. 페이로드 축소 효과와 함께 연결 5,000개에서의 전달 지연을 비교한다.

함께 다룰 튜닝 항목: 메시지 송신 스레드 풀(`clientOutboundChannel`), 느린 클라이언트 격리(`sendTimeLimit`, `sendBufferSizeLimit`), 하트비트 주기, OS 파일 디스크립터 한도

## 8. 범위 밖 (Out of Scope)

인터뷰에서 명시적으로 제외한 항목이다. 범위 폭주를 막기 위해 목록으로 남긴다.

- 자동 입찰(프록시 입찰)
- 조건부 낙찰
- 차순위 입찰자 승계
- 운영자의 특정 입찰 취소(롤백)
- 실제 PG 연동, 정산, 배송
- 이메일 알림
- 이벤트 소싱 기반 복구
- 진행 중인 회차의 동적 재편성
- C2C 마켓 부가 기능: 거래 채팅, 검색·카테고리·찜·추천, 소셜 로그인·본인인증, 평판(매너온도), 모바일 앱
- (스트레치) scale-out: Redis Pub/Sub, 레인 담당 인스턴스 선출

## 9. 리스크

### 9.1 실패할 이유 3가지

1. **병렬 개발한 결과물이 통합 단계에서 맞물리지 않는다.**
   AI 에이전트로 백엔드와 프론트엔드를 동시에 개발하면, 각자 다른 API 형태나 WebSocket 메시지 형식을 가정하고 만들기 쉽다. 이 어긋남은 통합할 때 한꺼번에 드러난다. 또 AI가 작성한 코드를 내가 이해하지 못하면 면접에서 설명할 수 없다.
   → 대응: **계약을 먼저 고정한다.** 1주차에 REST API(OpenAPI)와 STOMP 메시지 스키마를 `docs/`에 확정하고, 양쪽 에이전트는 이 계약을 기준으로만 작업한다. 프론트엔드는 목 서버로 먼저 개발한다. 레인 엔진과 동시성 처리 같은 핵심 코드는 직접 작성하거나 한 줄씩 리뷰한다.
2. **부하 테스트를 마지막에 몰아서 하다가 수치를 못 뽑는다.**
   측정 환경(k6 STOMP 스크립트, EC2, Grafana, NTP) 구축 자체가 며칠씩 걸린다. 마지막에 찾은 병목이 설계 문제이면 고칠 시간이 없다.
   → 대응: **4주차 말에 최소 기능만 이어 붙인 상태로 첫 부하 테스트**를 돌린다. 메트릭 계측은 처음부터 코드에 넣는다.
3. **레인 엔진의 정합성 버그가 끝까지 안 잡힌다.**
   타이머, 직렬 큐, 일시정지·재개, 재시작 복구가 얽힌 경합 조건은 재현이 어렵다. 시간이 흐르는 로직이라 테스트하기도 어렵다.
   → 대응: 레인 엔진을 Spring에 의존하지 않는 순수 도메인 코드로 작성한다. `Clock`을 주입받아 테스트에서 시간을 조작한다. "마지막 순간의 입찰 vs 타이머 만료" 경합 재현 테스트를 기능 구현보다 먼저 작성한다.

### 9.2 범위가 폭주할 위험 지점

| 지점 | 유혹 | 방어선 |
|---|---|---|
| 경매 규칙 | 자동 입찰, 조건부 낙찰, 차순위 승계 | 8장에서 제외로 확정 |
| C2C 마켓 기능 | 당근마켓을 레퍼런스로 삼았기 때문에 채팅, 검색, 찜, 평판으로 자연스럽게 번짐 | **제외 확정 (8장).** 출품 → 경매 → 결제의 한 줄 흐름만 구현 |
| 결제 | "어차피 PG 테스트 모드는 무료"라는 생각에 실제 연동, 정산, 환불까지 | 결제 연동 인터페이스 + 가짜 구현에서 멈춤 |
| 운영자 기능 | 자동 편성 알고리즘, 운영 통계 대시보드 | 운영자가 직접 편성 + 진행 제어 기능만 |
| scale-out | 수치를 키우고 싶어서 Redis Pub/Sub, 리더 선출 | 단일 인스턴스 목표를 달성하고 실험 2개를 마친 뒤에만 착수 |
| 장애 복구 | 이벤트 소싱으로 남은 시간까지 완전 복원 | 일시정지 상태로 복구 + 운영자 재개 |
